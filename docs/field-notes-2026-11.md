# 实测档案（2026-11-17 ~ 2026-11-19）

环境：i7-12800HX（24 逻辑核）/ RTX 4070 Laptop / 165Hz 屏；MuMu 6（MuMuPlayer-15.0-1，安卓 15）
2560×1440 dpi360、Vulkan、6 核 6GB、垂直同步关、帧率上限 144；工具 v0.3.4 便携版。

## 性能基线与调优轮次
| 轮次 | 设置 | 工具 CPU | 感知掉帧（基线 144） |
|---|---|---|---|
| 默认 | poll 16ms / ui 16ms | 主 1.05 核 + OCR worker 1.73 核 | ≈40 |
| 一轮 | poll 33 / ui 200 | OCR 0.36 核 | ≈10 |
| 二轮 | poll 100 / ui 200 | 主待机 0.03 核 | 用户接受（2026-11-19 定档） |

- 默认档 pprof：cgocall 43.5%（SDK 取帧+原生核心）、memmove 5.2%、nccSpansAVX2 4.8%、fyne 布局/光栅化 ≈4%。
- 宿主发现：电源计划原为"平衡"（2026-11-18 已切高性能，回退 GUID 381b4222-f694-41f0-9685-ff5bb260df2e）；
  VBS 运行中且 HVCI 开启（SecurityServicesRunning=2）；对局中 P 核 0,7 达 149%（单线程天花板）。
- 结论：掉帧主因是 CPU 侧持续负载挤占笔记本共享功耗预算 + SDK 每帧回读同步；GPU sm 仅 ~15% 是"活太少"，不是喂不饱。

## 采样定理与瞬态凹陷
豆 = 奥义/查克拉点（解包表 slot 401 奥义掉 4 豆），替身 = 查克拉 −1 的**代理信号**。
替身后立刻技能命中会 +1 补回，凹陷是瞬态。可检出最短凹陷 ≈ pollIntervalMs × minimumConfirmFrames：
16ms→~33ms；33ms→~66ms；100ms→~200ms。
实测：10Hz 下"秒替摸豆"有时漏报（用户确认并接受）；起跳后倒计时由单调时钟维持，与识别解耦，读出来就准。
候选下一步：minimumConfirmFrames 2→1 的 A/B（门槛减半，代价是单帧特效遮挡即误报）；
根治方向：改读替身按钮 CD 扫光（持久状态，hud_layout.json 已标技能钮 ROI，算法未实现）。
